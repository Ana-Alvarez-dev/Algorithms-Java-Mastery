# Build Artifacts

## Algorithms Java Mastery

Every software development process ultimately produces an output that can be executed, distributed, tested, or deployed. During Continuous Integration, source code is compiled, validated, and packaged into one or more files that represent the result of the build process. These files are known as **build artifacts**.

A build artifact is the tangible product generated by a successful build. In Java projects, artifacts commonly include executable **JAR** files, **WAR** files, test reports, documentation, code coverage reports, and packaged libraries. These artifacts provide a reproducible representation of a specific version of the software and can be stored, shared, deployed, or reused without rebuilding the project.

Professional CI/CD pipelines treat artifacts as first-class engineering assets. Rather than rebuilding an application every time it needs to be tested or deployed, the validated artifact generated by the pipeline is preserved and reused throughout the remainder of the software delivery process. This approach guarantees that the software deployed to production is exactly the same software that passed all automated validation stages.

Within the Java ecosystem, Maven generates build artifacts while GitHub Actions stores and distributes them between workflow stages. Understanding build artifacts is therefore essential for Continuous Delivery, deployment automation, cloud-native applications, and enterprise software engineering.

# 2. What Is a Build Artifact?

A **build artifact** is a file generated as the output of a successful software build.

Conceptually:

```text
Source Code
        ↓
Build Process
        ↓
Artifact
```

The artifact represents a validated version of the application that is ready for testing, distribution, or deployment.

---

# 3. Why Build Artifacts Exist

Without artifacts:

```text
Source Code

↓

Rebuild

↓

Deploy
```

Every deployment would require recompiling the project.

With artifacts:

```text
Source Code

↓

Build Once

↓

Artifact

↓

Reuse
```

The validated artifact can be deployed multiple times without rebuilding.

---

# 4. Artifact Generation

Artifacts are produced after successful validation.

Typical workflow:

```text
Compile
        ↓
Tests
        ↓
Quality Checks
        ↓
Package
        ↓
Artifact
```

Only software that successfully completes every validation stage produces an artifact.

# 5. Common Java Artifacts

Professional Java projects commonly generate:

- executable JAR files;
- WAR files;
- library JARs;
- test reports;
- documentation;
- coverage reports.

Each artifact serves a different purpose within the software lifecycle.

---

# 6. JAR Files

A **JAR (Java ARchive)** file packages compiled Java classes and resources into a single archive.

Conceptually:

```text
Java Classes
        ↓
Resources
        ↓
JAR File
```

Executable JAR files are commonly used for Spring Boot applications and command-line programs.

---

# 7. WAR Files

A **WAR (Web Application Archive)** packages Java web applications.

Conceptually:

```text
Web Application
        ↓
WAR File
```

WAR artifacts are typically deployed to servlet containers such as Apache Tomcat.

---

# 8. Reports as Artifacts

Not every artifact is an executable application.

CI pipelines frequently generate:

- test reports;
- benchmark reports;
- code coverage reports;
- static analysis reports.

Conceptually:

```text
Pipeline

↓

Report

↓

Artifact
```

These artifacts provide evidence of software quality.

---

# 9. Artifact Storage

After generation, artifacts are commonly uploaded to persistent storage.

Conceptually:

```text
Artifact

↓

Upload

↓

Storage
```

Artifact storage allows later retrieval without rebuilding the project.

---

# 10. Artifact Reuse

One artifact may be reused multiple times.

Example:

```text
Artifact

↓

Testing

↓

Staging

↓

Production
```

The same validated artifact moves through multiple deployment environments.

This guarantees deployment consistency.

---

# 11. Artifact Versioning

Professional software teams version their artifacts.

Examples include:

```text
1.0.0
```

```text
1.2.3
```

```text
2.0.0
```

Versioning enables traceability between source code, builds, and deployments.

---

# 12. Immutable Artifacts

Professional CI/CD pipelines treat artifacts as **immutable**.

Conceptually:

```text
Generate

↓

Store

↓

Never Modify
```

If changes are required, a completely new artifact is generated through a new build.

Immutability improves reproducibility and deployment reliability.

---

# 13. Relationship with Maven

Maven generates artifacts during the package phase.

Conceptually:

```text
Source Code
        ↓
Maven Package
        ↓
Artifact
```

Typical output includes:

- JAR;
- WAR;
- generated reports.

The generated files are usually placed inside the project's `target/` directory.

---

# 14. Relationship with GitHub Actions

GitHub Actions stores artifacts after successful pipeline execution.

Typical workflow:

```text
Workflow
        ↓
Generate Artifact
        ↓
Upload Artifact
        ↓
Later Download
```

Artifacts remain available for subsequent workflow stages or manual inspection.

---

# 15. Artifact Lifecycle

```text
Source Code

        ↓
```
